# 플레이스홀더 규약 `std-v1`

채우다 만 자리가 발행물에 남지 않게 하는 표기다. **규약 이름과 id 문법은 하나**로 두되
**표기만 파일 타입별로 이원화**한다.

## 왜 하나로 못 미는가

- `[대괄호]` 는 **마크다운 링크 문법과 충돌**한다.
  resume 가 `\[[^\]\n]{1,40}\]` 라는 억지 정규식으로 검출하고 있던 게 그 증거다.
- `{{중괄호}}` 는 **MDX 에서 JSX 표현식으로 파싱돼 빌드가 죽는다.**
  resume 의 기존 규약도 이미 `.mdx` 에서 `{{pos:}}` 사용을 금지하고 있었다.

둘 다 피하려면 표기를 나누는 수밖에 없다. **id 문법과 규약 이름을 하나로 유지**하는 것이
타협점이다 — 도구와 사람이 같은 이름으로 같은 것을 가리킨다.

## 표기

| 용도 | `.md` `.html` `.txt` `.pptx` | `.mdx` | 최종 산출물 |
| --- | --- | --- | --- |
| **채움 슬롯** | `{{ id }}` | `{/* @slot:id */}` | **0건 (FAIL)** |
| **집필 지시** | `<!-- @write: … -->` | `{/* @write: … */}` | 0건 |
| **조건 블록** | `<!-- @if: pos=cto -->…<!-- @end -->` | `{/* @if: pos=cto */}…{/* @end */}` | 0건 |
| **메타 힌트** | `<!-- @hint: rel=cto,po -->` | `{/* @hint: … */}` | 0건 |
| **집필 마커** | `@[제안]` `@[추정]` `@[창작]` `@[what-if]` `@[확인]` | 동일 | draft 만 |
| **엔진 블록** | ` ```viz ` · `<<meme:>>` · `(( ))` · `<Comp client:visible/>` | 동일 | **변경 없음** |

엔진 블록은 다른 도구가 소유한다. **건드리지 않는다.**

## 슬롯 id 문법

```
<section>.<field>[:<variant>]
```

`header.title` · `about.body:cto` · `exp.3.summary`

- `<section>` 은 **spec 의 `sections[].id`** 와 같아야 한다. 그래야 항목과 슬롯이 이어진다.
- `<variant>` 는 spec 의 `variants.keys` 중 하나.
- 반복 항목은 인덱스를 중간에 넣는다(`exp.3.summary`).

## 집필 마커

| 마커 | 뜻 |
| --- | --- |
| `@[제안]` | 소스에 근거가 없어 에이전트가 제안한 것 |
| `@[추정]` | 확인 못 한 값의 자리표시자 — **그럴듯한 숫자로 메우지 않기 위해 존재한다** |
| `@[창작]` | 에이전트가 주도해 쓴 부분 |
| `@[what-if]` | 아직 결론이 안 난 과제 |
| `@[확인]` | 사람 확인이 필요한 곳 |

draft 단계에서는 정상이고, **최종본에는 하나도 남으면 안 된다.**

## 검사

```bash
lint_placeholders.py check <파일> --spec <id> --stage draft   # 지시·마커 허용, 미해결만 보고
lint_placeholders.py check <파일> --spec <id> --stage final   # 전부 0이어야 통과
lint_placeholders.py import <템플릿> --out template.slots.json
```

`--stage final` 에서 슬롯·집필 지시·메타 힌트·집필 마커·미해결 조건 블록이 하나라도 있으면 실패한다.

## 레거시 — 기존 산출물은 건드리지 않는다

완료 판정은 **"새 템플릿 100% 가 std-v1"** 이지 **"전 파일이 std-v1"** 이 아니다.
이미 발행된 글과 운영 중인 템플릿을 다시 만지는 것은 얻는 것보다 잃을 위험이 크다.

| 표기 | 어디서 | 조치 |
| --- | --- | --- |
| `[…]` 대괄호 슬롯 | resume 템플릿 | `legacy_accept: ["bracket-inline"]` 로 통과 |
| `{{pos:키}}` · `<!-- pos:… -->` | resume 직무 분기 | `legacy_accept: ["pos-block"]` |
| `{중괄호 서술형}` | code_test 캔버스 | `legacy_accept: ["brace-descriptive"]` |
| `s0001` 위치 키 | resume 템플릿 슬롯맵 | `legacy_accept: ["ordinal"]` |

spec 의 `placeholders.legacy_accept` 에 넣어 두면 린터가 경고만 내고 통과시킨다.
넣지 않으면 `--stage final` 에서 실패한다 — **모르고 섞이는 것과 알고 두는 것을 가른다.**

## 새 템플릿을 만들 때

- 슬롯 id 를 spec 의 항목 id 와 **반드시 맞춘다.** 안 맞으면 나중에 무엇을 채워야 하는지 모른다.
- 집필 지시(`@write`)에는 **직무**를 적는다. "여기에 내용" 같은 지시는 없느니만 못하다.
- 조건 블록은 **짝을 맞춘다.** 린터가 열림/닫힘 수를 세서 어긋나면 실패시킨다.
