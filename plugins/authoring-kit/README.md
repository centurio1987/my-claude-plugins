# authoring-kit

집필 규칙을 **한 곳에서** 관리하는 플러그인. 블로그·해설서·이력서처럼 매체가 달라도
"어떻게 쓰는가"는 한 벌로 두고, "이 매체로 어떻게 내보내는가"만 프로젝트에 남긴다.

## 왜 만들었나

세 프로젝트가 같은 집필 파이프라인을 각자 한 벌씩 들고 있었다.

```
리서치 → 집필 → 외부검토 → 품질게이트(보완 루프 ≤3R) → 발행
```

복제는 그 자체로도 문제지만, 실제로 사고를 냈다.

- **같은 퍼소나가 두 프로젝트에 복사돼** 각자 갈라지고 있었다.
  두 파일은 문체 규칙 10개와 금지 목록이 문자 단위로 같은 문서였다.
- **한 사람의 문체가 공통 원칙 자리에 놓여** 전역 최우선으로 승격돼 있었다.
  결과적으로 AI 퍼소나가 쓴 글에도 그 사람의 만연체·당위 마무리·한자어 인용이 강제됐다.
- **같은 규칙 문서가 세 판본으로 갈라져** 한쪽에만 있는 조항이 생겼다.
- **품질 루브릭이 폐기된 템플릿의 섹션을** 여전히 MUST 로 요구하고 있었다.

전부 에러 없이 조용히 굴러가던 것들이다. 결과물을 봐야 알아차린다.

## 어떻게 푸는가 — 갈래(axis) 소유권

층에 **서열을 매기지 않는다.** 서열을 매기면 "누가 이기냐"가 층 단위로 전파되어,
한 사람의 문체가 전역이 되는 사고가 그대로 재발한다.
대신 **갈래마다 소유 층을 하나로 못박고, 소유자만 그 갈래의 규칙을 쓴다.**

| 축 | 소유 | 내용 |
| --- | --- | --- |
| `evidence` | **L0** (불가침) | 미검증 수치·출처 없는 단정 금지 |
| `grammar` | **L0** (불가침) | 번역투·이중 피동·무생물 주어 |
| `comprehension` | **L0** (불가침) | 점진적 공개·약어 풀어쓰기·미정의 용어 |
| `machine-rhythm` | **L0** 탐지 + **L1** 면제 | AI 기계 리듬 |
| `register` `rhythm` `device` `lexicon` | **L1** voice | 저자 고유의 목소리 |
| `structure` `scope-principle` | **L2** spec | 글 종류의 골격과 원칙 |

소유자가 아닌 층이 그 갈래를 쓰면 `validate` 가 **갈래 위반**으로 죽인다.
`evidence`·`grammar`·`comprehension` 은 **어떤 퍼소나도 면제받지 못한다**(hard floor).
협상 가능한 것은 `machine-rhythm` 뿐이고, 그것도 코드별로 사유와 한계를 적어야 한다.

## 세 층은 어디에 사는가

```
플러그인 assets/          ① upstream 기본값 (읽기 전용)
~/.claude/authoring/      ② 사용자 레지스트리 — voice 는 프로젝트를 넘나든다
  principles/  voices/<id>/
<project>/.claude/authoring/   ③ 프로젝트 — spec 은 경로·명령에 묶인다
  specs/<id>/  paths.json
```

같은 파일명이면 ③ > ② > ①. `spec` 은 **논리만** 담고 경로·빌드명령은 `paths.json` 이 갖는다 —
그래야 같은 명세를 다른 프로젝트에서 쓸 수 있다.

## 스킬

| 스킬 | 하는 일 |
| --- | --- |
| `authoring-write` | 집필 오케스트레이터. **규칙 전문을 읽지 않고** 요약만 보고 워커에 위임한다 |
| `authoring-spec` | 글 명세 등록 — 항목·작성법·범위원칙·퍼소나·템플릿 |
| `authoring-voice` | 퍼소나 등록. 역추출 시 **모수를 먼저 의심**하게 만든다 |
| `authoring-gate` | 채점 + 보완 루프 ≤3R. **자동 통과 없음** |
| `authoring-doctor` | 조용히 잘못 도는 상태 진단 |
| `authoring-method` | 워커 전용 방법론 (사용자에게 뜨지 않는다) |

### 컨텍스트 예산

공통 원칙 전문은 1000줄이 넘는다. 메인 스레드가 그걸 안고 가면 글 쓸 예산이 남지 않는다.

```bash
authoring.py resolve --voice <id> --spec <id> --profile main     # ≈120줄 — 골격·원칙·요약·코드 목록
authoring.py resolve --voice <id> --spec <id> --profile worker   # 전문 — 집필·채점 워커가 읽는다
```

## 설계 원칙 넷

1. **조용한 실패를 만들지 않는다.** 못 읽은 파일을 "깨끗하다"고 하지 않고,
   사유 없는 면제를 받지 않고, 미해결 충돌에서 한쪽을 임의로 이기게 하지 않는다.
2. **공통 원칙에 저자 이름이 한 줄도 남으면 안 된다.** 남으면 모든 퍼소나에 샌다.
3. **재작성은 허용하되 유실은 안 된다.** 이관은 복사가 아니라 재작성이므로,
   옮긴 규칙은 목적지를 명시하고 버린 규칙은 사유를 남긴다.
4. **기존 산출물을 건드리지 않는다.** 새 규약은 앞으로 쓰는 것에만 적용하고,
   기존 표기는 `legacy_accept` 로 통과시킨다.
